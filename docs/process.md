## Одна картинка

```
   Bitrix24 (CRM)                      polls                              Клиент
 сделка/лид/смарт-процесс   ──►   снимок контекста + приглашение   ──►   проходит опрос
 доходит до стадии направления    → «настраиваемое дело» в              /s/:ключ (контур A)
 (триггер)                          таймлайне сделки: ссылка +               │
                                    кнопка «Отправить приглашение»          │ ответы
                                                                            ▼
 клиент заполнил  ◄── (триггер завершения) ── результат в таймлайн     дашборд /d/:ключ
                                              + в аналитику       ◄──  (контур B): NPS/CSAT/срезы
```

**Формула:** Датчик (событие CRM) → Опрос → Аналитика (KPI / Лента портала). Опрос — самый дешёвый
датчик; ценность — в аналитике и AI-разборе ответов.

## Два контура

- **Контур A — прохождение опроса** (`/s/:ключ`). Кто: клиент. Что видит: Интро → вопросы → «Спасибо».
  Анонимно, без авторизации, ~5–7 минут, можно вернуться и дозаполнить. Ссылка живёт в пределах
  **срока доступности** опроса (настраивается, см. ниже).
- **Контур B — дашборд аналитики** (`/d/:ключ`). Кто: сотрудник компании (внутри Bitrix24). Что видит:
  NPS/CSAT/распределения, тренд по месяцам, срезы по клиенту·услуге·направлению·ответственному,
  сравнение «до/после» между версиями. Закрыт авторизацией портала.

## Жизненный цикл — по шагам

### 1. Опрос создаётся и публикуется ✅

Опрос собирается в **конструкторе** (`/admin/surveys`) или программно и **компилируется** в иммутабельную
версию с номером. Стабильные ключи (`question_key`/`option_key`) → версии v1 и v2 **сопоставимы** в
аналитике (правка текста — тот же ключ; смена смысла — новый ключ). Опубликованную версию нельзя переписать.

У каждого опроса — свои **настройки запуска** (какие направления/стадии его триггерят) и **срок
доступности ссылки** (см. §Управление опросами).

### 2. Датчик — что и когда запускает опрос

- **Автоматически по стадии направления.** Сущность (сделка/лид/смарт-процесс) доходит до триггер-стадии
  своего направления → Bitrix шлёт событие → сервер снимает контекст (`crm.<entity>.get` + товары).
  Разным `(направление, стадия)` можно назначить **разные опросы**. Статус: 🟡 для **сделки**
  (`event.bind ONCRMDEALUPDATE` → `/api/b24/deal-update`, ждёт живого smoke); ⏳ для **лида/смарт-процесса**
  (ядро-маппер готов — `entity-event.ts`/`entityGet`, нужен эндпоинт события); ⏳ UI-маппинг
  `(направление, стадия) → опрос` в конструкторе (сейчас — по типу сущности через env).
- **Вручную из карточки** — встройка-виджет в области дел сущности (`CRM_DEAL_DETAIL_ACTIVITY`):
  сотрудник жмёт «Запустить опрос» → тот же снимок контекста. Статус: 🟡 для сделки.
- **Задачи как источник — НЕ поддерживаются** (убраны из скоупа).

### 3. Приглашение и доставка через «настраиваемое дело» ⏳

Из снимка контекста создаётся **приглашение** с одноразовым токеном (пинит версию анкеты — публикация
новой версии не влияет на уже отправленные). Доставка задумана **средствами Bitrix**, а не своим email/SMS:

- в **таймлайн сделки** пишется **настраиваемое дело** (`crm.activity.configurable.add`) — блок с текстом,
  ссылкой на опрос и **кнопкой «Отправить приглашение»**;
- виджет `CRM_DEAL_DETAIL_ACTIVITY` это рисует и ловит клик (`setLayout` + `bindLayoutEventCallback` +
  `setPrimaryButtonState`); менеджер жмёт кнопку → ссылка уходит клиенту (канал — по настройке).

Статус: ⏳ (референс `crm.activity.configurable` — `ai-price-import/server/utils/configurableActivity.ts`).
Сейчас `deal-invite` просто возвращает ссылку-токен, «дело» ещё не создаёт.

### 4. Клиент проходит опрос (контур A) ✅

Страница `/s/:ключ`: берёт текущую опубликованную версию (`GET /api/survey/:key/current` — без
CRM-конфигурации) → одноразовый `nonce` → клиент отвечает (прогресс в `localStorage`, возврат/deep-link)
→ `POST /api/submit` через конвейер защиты: **honeypot → rate-limit → nonce (анти-replay) → версия →
валидация → приглашение (токен → снимок CRM, одноразовый) → запись** с серверными `id`/временем.
Ссылка действительна **в пределах срока доступности** опроса; повтор по токену → `409`.

### 5. Триггер «клиент заполнил опрос» ⏳

По завершению анкеты — симметрично запуску: сводка (NPS/CSAT + ключевые ответы) возвращается **в таймлайн
сделки** отдельным настраиваемым делом со ссылкой «Открыть результат», и результат попадает в аналитику.
Статус: ⏳ (связано с #18 — результат → таймлайн + просмотр/PDF).

### 6. Аналитика (контур B) ✅

Дашборд `/d/:ключ` считает на лету: **NPS** / **CSAT** / **CES**, распределения (с человекочитаемыми
метками), **4 уровня** (по опросу · услуге/товару · клиенту помесячно · направлению + KPI ответственных),
**тренд NPS** через границу версий, **фильтр по версии** (`?version=N`) для сравнения «до/после».

### 7. Приватность встроена ✅

- **Малые выборки подавляются** (`ANONYMITY_THRESHOLD = 5`) — нет «NPS по одному ответу».
- **Tenant-изоляция**: портал видит только свои данные (`portalId`).
- **Дашборд fail-closed**: без валидной сессии портала агрегаты не отдаём.
- Опросы клиентов режем по сделке; опросы сотрудников (eNPS/пульс) — анонимно.

## Связка с Bitrix24 (кратко)

- **Установка** сохраняет OAuth-токены портала (шифр), регистрирует виджеты и авто-триггер `event.bind`
  (робот `bizproc.robot.add` пока НЕ регистрируется — его эндпоинт `/api/b24/robot` не реализован, #122).
  Статус: 🟡 код, ждёт живого install-smoke.
- **Дашборд во фрейме** проходит handshake (`BX24.getAuth` → подписанная сессия-cookie). 🟡 код.
- **Настраиваемые дела** в таймлайне — доставка приглашения (шаг 3) и возврат результата (шаг 5). ⏳.
- **Деплой** — два таргета: (a) Docker + GHCR + watchtower + nginx-proxy + TLS ✅; (b) **Bitrix24 Vibecode
  «Чёрная дыра»** ⏳ — один Nitro-процесс без nginx, безопасность на уровне приложения (`APP_EDGE_SECURITY`);
  референс — `ai-price-import/docs/DEPLOY_VIBECODE.md`.

## Управление опросами (для оператора)

### Как устроен опрос

Опрос = черновик (`SurveyDraft`) → `compile()` → иммутабельная опубликованная версия. «Сохранить» =
**опубликовать новую версию** (`currentVersionNo + 1`). Отдельной таблицы черновиков нет.

### Как вносятся и правятся вопросы ✅

**Конструктор** `/admin/surveys` (под авторизацией портала, fail-closed):

1. **Список опросов** (`index.vue`) — с фильтром; **конструктор одного опроса** (`[key].vue`) грузит
   текущую версию как черновик.
2. В конструкторе: **добавить / удалить / переставить** вопросы и опции, сменить **тип** (`single`/`multi`/
   `text`), **метрику** (`nps`/`csat`/`ces`/…), обязательность, задать **баллы** опций, править
   заголовок/стадии-триггеры. Логика — в ядровом `~core/client/survey-editor` (под тестами), страница
   лишь держит реактивное состояние.
3. **Публикация** новой версии с оптимистичной блокировкой (`expectedVersionNo` → `409` при гонке).
   Новому вопросу генерируется стабильный `question_key`; у существующих ключи сохраняются → старые ответы
   остаются сопоставимыми. Дашборд берёт вопросы **по метрике из текущей версии**, так что новый вопрос
   сразу попадает в срезы.

Другие способы завести опрос: **сид** (`src/demo/seed.ts`, для тестов) и **программно**
(`store.publish(draft, versionNo)`).

### Какой опрос запускается по какой сущности/стадии

- Сейчас: по **типу сущности** через env (`SURVEY_KEY_DEAL`/`SURVEY_KEY_LEAD`/…, дефолт `SURVEY_KEY_DEFAULT`),
  + стадии-триггеры в самой версии опроса (`invitationPolicy.triggerStages`, формат `C{направление}:СТАДИЯ`).
- ⏳ План: UI-маппинг **`(направление, стадия) → опрос`** в конструкторе — «разным стадиям разных
  направлений разные опросы» без правки env.

### Срок доступности ссылки на опрос ⏳

Настраивается **на каждый опрос** — от **5 минут до 5 дней**. После истечения ссылка не открывается
(приглашение просрочено). Кладётся в `invitationPolicy` версии, применяется на `/api/submit` и на выдаче
страницы. Статус: ⏳ (поле схемы + проверка на границе).

### Как удалить данные за период ✅

Ручная SQL-операция (кнопка «очистить период» — отдельная задача), по нужному порталу и периоду, с бэкапом:

```sql
delete from response
 where portal_id = (select id from portal where member_id = '<member_id>')
   and submitted_at < '2026-01-01T00:00:00Z';
```

`response_product` удалится каскадом (FK); `survey_version` не трогаем. Полная очистка портала —
`delete from response where portal_id = …`.

## Где что хранится

- **Опросы** (версии + вопросы + опции) и **результаты** (ответы + снимок контекста сделки) хранятся в
  **PostgreSQL на твоём сервере**. Демо-режим «в памяти» из рантайма **убран** — приложение всегда работает
  на БД (in-memory остаётся только для юнит-тестов, чтобы не требовать живую БД).
- **Объём — очень маленький** (это текст): опрос — несколько КБ, один ответ — ~1–2 КБ. Даже десятки тысяч
  ответов — единицы-десятки МБ. Диск сервера это почти не нагружает.
- **Что можно держать на стороне Bitrix24:** снимок результата — в **таймлайне сделки** (настраиваемое
  дело), тяжёлые вложения/файлы — на **Диске Б24**. Но «источник правды» для аналитики (кросс-версионные
  срезы, тренды) держим у себя — Б24 их не посчитает. Подробнее — ответ в диалоге.
