# Разбор старого коробочного решения заказчика

Материал для адаптера миграции. Источник: портал `portal.aidapioneer.by`, модуль `shef.questionary`,
инфоблок 67, highload-блоки `sh_qest_h_*`, настройки в `b_option`.

Все цифры получены выборками на живом портале 2026-08-29. Контур переноса — в
`docs/PROCESS.md`, раздел «Миграция как отдельная услуга».

---
## 18. Разбор старой коробочной версии

Модуль `shef.questionary` (+ `shef.b24base`), компоненты `questionary.pub`,
`questionary.setting.structure`, `questionary.setting.fields`, публичные страницы
`/questionary/pub/` и `/questionary/setting/*`, отдельный шаблон сайта на базе `landing24`.
Портал — `portal.aidapioneer.by`.

### Где лежали данные

Одной таблицы нет, поэтому и одного `SELECT` не будет — хранилища три:

1. **Инфоблок 67 «Анкеты»** (`VERSION = 2`, то есть свойства в `b_iblock_element_prop_s67`
   колонками `PROPERTY_<ID>`) — карточка анкеты, одна на отправку:

   | Свойство | ID | Смысл |
   |---|---|---|
   | `STATUS` | 362 | Черновик `NEW` → В работе `WORK` → Ожидает заполнения `FILL` → Закрыт `CLOSE` |
   | `DEAL` / `CONTACT` | 363 / 395 | привязка к CRM |
   | `TYPE` | 364 | тип анкеты, значим `XML_ID` |
   | `PRODUCT` / `PROCESS` / `PERSONAL` | 365 / 366 / 367 | рассчитанные средние по секциям |
   | `SEND_DATE` | 368 | по факту — дата **заполнения**: ставится в `saveDataId()` |
   | `DATE_C_SEND` | 370 | настоящая дата отправки клиенту |
   | `MEETING` | 369 | встреча |
   | `HASH` / `DATA_ID` | 371 / 372 | ключ публичной ссылки / строка с ответами |

2. **Highload-блоки `sh_qest_h_<код>`** (класс `ShefQuestionare<код>`) — сами ответы,
   отдельный HL-блок на каждый тип анкеты, каждый вопрос = пользовательское поле `UF_*`;
   формулировка вопроса живёт в `EDIT_FORM_LABEL` этого поля и больше нигде.
3. **`b_option` модуля `shef.questionary`** — реестр типов (`questionary_list`) и структура анкет
   (`questionary_group_<тип>`: секции, поля, типы, веса, интерпретации). Реестр, к слову, повреждён:
   на верхнем уровне лежат `CODE`/`TABLE`/`ID` первого типа (с `ID: 15`, хотя фактический HL-блок
   digital — 16) вперемешку с картой остальных. Формат менялся на ходу, миграции не было.

### Модель вопросов и оценки (то, что мы откладывали — вот факт)

Типов вопросов ровно три:

| TYPE | Хранение (UF) | Виджет | SETTING |
|---|---|---|---|
| `POINT` | `double` | ползунок MIN…MAX (в примере 0–10) | `MIN`, `MAX`, `SIZE` — вес в % |
| `TEXT` | `string` | textarea | — |
| `DATE` | `date` | дата | `TYPE: FUTURE` |

Оценка (`Item::calcStructData`): по каждой секции суммируется `значение × SIZE / 100` только для
полей типа `POINT`; результат округляется до 2 знаков и пишется в свойство инфоблока, указанное в
`FIELD` секции. Общего итогового балла по анкете нет — только три балла по секциям.

Плюс `TERMS` — диапазоны `MIN`/`MAX` с текстом: по набранному баллу секции респонденту показывается
словесная интерпретация. Логика диапазонов живёт только во фронтенде (`body.php: termsResult`).

**Анкет не одна, а двенадцать** — по направлениям агентства: `DIGITAL`, `DESIGN`, `CONCEPT`,
`BRAND`, `VIDEO`, `GAME`, `MEDIA`, `CREATIVITY`, `STRATEGY`, `PACKAGE`, `IDENTITY`,
`PRODUCTIONSUPERVISION`. Все построены по одному каркасу:

| Секция | Куда пишется балл | Содержимое |
|---|---|---|
| Продукт | `PROPERTY_PRODUCT` | 3–5 балльных вопросов |
| Процессы | `PROPERTY_PROCESS` | 1–3 балльных вопроса |
| Персонал | `PROPERTY_PERSONAL` | 2–3 балльных вопроса |
| Вопросы / Открытые вопросы | — | 2–3 текстовых, в балл не идут |

Исключение — `DIGITAL`: секции «Продукт» у него нет вовсе, только Процессы и Персонал.

Что показала сверка всех структур:

- **Веса везде дают ровно 100.** Ни одной секции с суммой ≠ 100 по всем 12 анкетам. Шкала у всех
  балльных вопросов одна — `MIN 0`, `MAX 10`. Значит балл секции — честное взвешенное среднее в
  шкале 0–10, и стратегия `weighted` переносится в новое решение один в один.
- **Вес 0 как способ выключить вопрос из оценки.** `UF_HQ_PERS_CREAT` в `concept` и `design`,
  `UF_HQ_IDENTITY_8` в `identity`: вопрос задаётся, ответ сохраняется, в балл не идёт. Замысел
  понятен, но выражен неотличимо от опечатки — в новой модели это отдельный флаг, а не вес 0.
- **Ошибка в `game`:** `UF_HQ_PROC_REG` стоит в двух секциях сразу — в «Продукте» с весом 50 и в
  «Процессах» с весом 40. Один ответ клиента влияет на два балла. В новой схеме уникальность ключа
  вопроса внутри версии проверяется валидатором.
- **`TERMS` заполнены только у `DIGITAL`** — 6 диапазонов на «Процессы» и «Персонал»: 4–6 «Где-то мы
  свернули не туда», 6–7.5, 7.5–8, 8–8.5, 8.5–9.4, 9.4+ «Мы на вершине!». Ниже 4 не покрыто ничем —
  клиент с плохой оценкой не видит никакого текста. И хранится это как готовый HTML с классами
  `landing24` (`g-color-white g-font-size-16 text-center`).
- **Типы по факту:** `POINT` — 91 вопрос, `TEXT` — 22, `DATE` — **один** (`UF_HQ_QUEST_NDATE` в
  `media`). Тип `DATE` практически мёртв, тащить его в v1 смысла нет.
- **Общая библиотека вопросов.** `UF_HQ_PERS_INVOL`, `UF_HQ_PERS_PROF`, `UF_HQ_QUEST_LIKE`,
  `UF_HQ_QUEST_RECOM` встречаются в 6 анкетах каждый, `UF_HQ_PROC_SP_DEV`/`_REW` — в 5. То есть
  вопросы осознанно переиспользуются между направлениями, чтобы результаты были сравнимы.
- **Два поколения именования.** Старое семантическое (`UF_HQ_PROD_ANALYT`, `UF_HQ_PERS_PROF`) и
  новое порядковое (`UF_HQ_IDENTITY_1…10`, `UF_HQ_PACKAGE_1…12`, `UF_HQ_STRATEGY_*`,
  `UF_HQ_CREATIVITY_*`, `UF_HQ_PRSUP_*`). У второго поколения код не несёт смысла вообще —
  формулировка есть только в подписи поля.
- **Формулировки длинные и содержательные**: «профессионализм account менеджера (понимание задач
  проекта, качество ответов на вопросы, качество консультаций)». Вопрос — это абзац, а не ярлык.

### Что показали накопленные данные

247 анкет за 4,5 года (2022 → август 2026), из них заполнено 196. Это один портал одного агентства,
то есть **нагрузка мизерная — примерно 55 анкет в год**. Очередь в новом решении нужна ради
надёжности и троттлинга REST, а не ради производительности; раздувать её не надо.

**Конверсия падает, а напоминаний нет.**

| Год | Отправлено | Заполнено | Конверсия |
|---|---|---|---|
| 2022 | 6 | 6 | 100 % |
| 2023 | 30 | 30 | 100 % |
| 2024 | 83 | 66 | 80 % |
| 2025 | 95 | 67 | 71 % |
| 2026 (неполный) | 33 | 27 | 82 % |

Итого 51 приглашение так и висит в статусе «Ожидает заполнения». Пока анкет было мало, менеджер
дожимал каждую руками; с ростом объёма механизм перестал работать. Вывод для нового решения:
**авто-напоминание — не украшение, а обязательная часть v1.**

**Шкала 0–10 работает, но не так, как задумывалась.** Сырое распределение всех 2411 балльных
ответов (не усреднённых, а как их поставил клиент):

| Оценка | Ответов | Доля |
|---:|---:|---:|
| 0 | 52 | 2,2 % |
| 1 | 17 | 0,7 % |
| 2 | 13 | 0,5 % |
| 3 | 25 | 1,0 % |
| 4 | 23 | 1,0 % |
| 5 | 50 | 2,1 % |
| 6 | 65 | 2,7 % |
| 7 | 175 | 7,3 % |
| 8 | 313 | 13,0 % |
| 9 | 560 | 23,2 % |
| **10** | **1118** | **46,4 %** |

Среднее 8,63. Половина ответов — десятка, 83 % — восьмёрка и выше. Как непрерывная метрика шкала
бесполезна: между «хорошо» и «отлично» она не различает. Но у распределения есть отчётливая форма —
и она в точности NPS-образная:

| Группа | Ответов | Доля |
|---|---:|---:|
| 9–10 | 1678 | 69,6 % |
| 7–8 | 488 | 20,2 % |
| 0–6 | 245 | 10,2 % |

Индекс «доля 9–10 минус доля 0–6» даёт **59** — осмысленное, устойчивое число, которое можно
сравнивать между направлениями и следить за ним во времени. Оговорка: это NPS-*подобная*
группировка, а не канонический NPS — тот считается по одному вопросу «порекомендуете ли». Но границы
корзин совпали с естественными разрывами в данных, так что заимствование здесь честное.

Отсюда решение по метрике: **шкалу 0–10 оставляем, среднее убираем из главных чисел, считаем доли.**
Порог тревоги — любой ответ 6 и ниже: таких 245 за 4,5 года, около 55 в год, вполне обрабатываемый
поток сигналов для менеджера. Это и есть рабочий алерт, а не «средний балл 8,6».

**И баг, который портит эти данные.** Нулей 52 — больше, чем единиц (17), двоек (13), троек (25) и
четвёрок (23). Для монотонно убывающего к низу распределения это аномалия, и её причина видна в коде
виджета: `data()` отдаёт пустое значение, `created()` тут же ставит `SETTING.MIN` (то есть 0), а
`watch` на этом переходе `'' → '0'` уже эмитит `set:field`. **Нетронутый ползунок отправляется как
честный ноль.** Отличить «клиент поставил 0» от «клиент пропустил вопрос» в накопленных данных
невозможно.

Требование в новое решение: у балльного вопроса нет предустановленного значения, «нет ответа» —
это `null`, а не крайнее значение шкалы, и обязательность проверяется явно.

**Треть ответов осиротела.** В HL-таблицах 295 строк с ответами, а карточек анкет со ссылкой на них —
196. Разница в 99 строк — это ответы, чьи карточки в инфоблоке удалили: сами ответы остались, а
привязка к сделке, клиенту и дате исчезла вместе с элементом. Хуже всего у `concept` (70 строк
против 33 карточек) и `digital` (18 против 2); у `game` и `media` карточек нет вовсе, а строки с
ответами есть.

Отсюда два требования. Первое: удаление должно быть каскадным или мягким — осиротевшие ответы это
мусор, который ещё и врёт статистике. Второе, важнее: **ответ обязан нести собственный снимок
контекста** — компания, сделка, ответственный, дата на момент прохождения, — а не зависеть от живой
карточки в CRM. В новой модели это `responses.meta`, и заполняется он в момент ответа.

Это же заставляет пересмотреть вывод про `DIGITAL`. По живым карточкам выходило «направление мертво,
15 % конверсии». На деле в `sh_qest_h_digital` 18 заполненных строк, причём с текстовыми ответами во
всех восемнадцати. Анкеты проходили — это карточки массово удалили. Правильная формулировка: не
направление умерло, а история по нему потеряна.

Что остаётся верным про `DIGITAL`: `TERMS` настроены только у него, и обе анкеты, дожившие до
карточки, дали 2,70 по процессам и 4,00 по персоналу — то есть **провалились в непокрытую зону ниже
4 и не показали клиенту никакого текста**. Дыра в покрытии диапазонов сработала в 100 % случаев,
которые можно проверить.

### Какие вопросы работают, а какие — ритуал

Разрез по 94 вопросам показывает: разброс между вопросами больше, чем между анкетами.

| Доля оценок 9–10 | Вопросы |
|---|---|
| 94–97 % | `package` 7–10, «вовлечённость аккаунт-менеджера» в `concept` и `video` |
| 45–61 % | почти весь блок `creativity`, «организация» в `design`, «оригинальность идеи» в `concept` |

Вопрос, на который 96 % клиентов ставят 9 или 10, не измеряет ничего — он ритуал. А
`UF_HQ_CREATIVITY_3` («масштабируемость решения») с долей 45 % и одиннадцатью низкими оценками из
44 — рабочий инструмент. Практическое правило для новых шаблонов: **вопрос, у которого доля 9–10
выше 80 %, кандидат на удаление** — он занимает время клиента и не даёт информации.

Нули, кстати, кучкуются не равномерно: 11–12 % в `UF_HQ_CREATIVITY_3`, `UF_HQ_PACKAGE_4`
(«техническая вёрстка и подготовка в печать») и трёх вопросах `digital`. Это ровно те вопросы, на
которые клиент часто не может ответить по существу — и, не тронув ползунок, отправляет ноль.
Ещё один довод за явное «затрудняюсь ответить» вместо молчаливого нуля.

### Открытые вопросы: критику пишут реже, но вдвое длиннее

| Анкета | «Что понравилось» | «Что улучшить» | Средняя длина: понравилось / улучшить |
|---|---|---|---|
| `package` | 71 % | 35 % | 137 / 165 |
| `creativity` | 66 % | 45 % | 120 / 248 |
| `design` | 48 % | 39 % | 135 / 215 |
| `brand` | 54 % | 38 % | 149 / 378 |
| `productionsupervision` | 81 % | 81 % | 111 / 219 |

Закономерность устойчивая: до вопроса «что улучшить» доходит примерно вдвое меньше людей, зато те,
кто отвечает, пишут в полтора-три раза длиннее. Максимум — 1526 символов. Это не отписки, а
развёрнутая обратная связь, и она ценнее всех баллов вместе взятых.

Что из этого следует для приложения: текстовый ответ — первоклассный объект, а не приложение к
цифре. Он должен целиком попадать в таймлайн CRM (не обрезанным до превью), участвовать в поиске и
быть виден в отчёте рядом с баллом. И раз «что улучшить» заполняют вдвое реже — этот вопрос
заслуживает отдельного внимания в вёрстке: не последним в длинной форме, а с явным приглашением.

Ещё из наблюдений: у `DIGITAL` колонка среднего по продукту пуста — подтверждает, что секции
«Продукт» у него действительно нет. Слабее всех выглядят `PRODUCTIONSUPERVISION` (7,67 / 6,67 / 6,67
в 2024) и `STRATEGY`; `CREATIVITY` заметно растёт год к году (7,07 → 8,48 → 8,93 по продукту).

### Что забираем в новое решение

- **Секции с весами и словесной интерпретацией по диапазонам.** Это рабочая, обкатанная модель —
  переносим как первую стратегию оценки `weighted` (веса в %, диапазоны → вердикт), только считаем
  на сервере, а не в браузере.
- **Ползунок как основной виджет** для балльных вопросов и свободный текст «что понравилось /
  что улучшить» — это то, чем реально пользовались.
- **Автоподстановка контекста в шапку анкеты**: компания, сделка, ответственный, бренд. Респондент
  видит, о чём его спрашивают. В новом это данные приглашения, снятые на момент отправки.
- **Анатомию анкеты: общая рамка плюс сменный блок.** Формулировки из подписей полей показывают,
  что специфична только секция «Продукт» — там вопросы про суть направления («качество продакшн-брифа
  (структурность, полнота, наличие референсов)», «техническая вёрстка и подготовка в печать»,
  «аналитический блок (качество проработки, выводы)»). Остальные три секции почти одинаковы во всех
  анкетах:

  | Секция | Вопросы | Насколько универсальны |
  |---|---|---|
  | Продукт | 3–5 | своё для каждого направления |
  | Процессы | 1–3 | «скорость разработки», «скорость внесения правок», «скорость документооборота» |
  | Персонал | 2–3 | вовлечённость и профессионализм аккаунт-менеджера + «команда \<отдела\>» |
  | Открытые вопросы | 2 | «Что понравилось…», «Что вы рекомендуете улучшить?» — сквозные |

  Значит шаблон опроса в новом решении — это общая рамка с подстановкой (название отдела меняется:
  креативного / дизайн- / стратегического) плюс сменный блок под направление. Не 12 независимых
  анкет, а один каркас в 12 вариантах.

- **Библиотеку переиспользуемых вопросов — с версиями формулировок.** Один и тот же по смыслу
  вопрос существует в двух редакциях: старая «вовлеченность account менеджера в проект (скорость
  ответа на вопросы, скорость документооборота)» и новая «вовлеченность аккаунт-менеджера
  (оперативность коммуникации, глубина погружения в проект и в задачи)». Формулировку меняли, а
  сравнивать результаты хочется сквозь эту границу. Отсюда требование: вопрос — отдельная сущность
  с устойчивым идентификатором и версионируемым текстом, подключаемая в несколько опросов.

- **Соглашение о нумерации.** В новых анкетах `SORT` кодирует секцию: 1xx — Продукт, 2xx — Процессы,
  3xx — Персонал, 4xx — открытые вопросы. В старых (`brand`, `concept`) сортировка сбита — у трёх
  полей подряд один и тот же `SORT 600`, а в `concept` у всех `100`, то есть порядок вопросов там
  фактически случайный. Порядок в новом решении — явное поле, а не побочный эффект.
- **Структуру анкет из `b_option`** — прямой донор для сидов шаблонов: JSON уже есть, маппится в
  `survey_versions.schema` почти один в один.

### Что не переносим — и почему

- **HL-блок и UF-поле на каждый вопрос.** В коробке это давало типизацию и штатные списки, но в
  облачном мультипортальном приложении означало бы DDL (создание таблиц и полей) на каждый новый
  опрос каждого портала. Заменяем на `answers.value jsonb` + схема в `survey_versions`. Заодно
  бесплатно получаем версионирование, которого в коробке нет вообще: правка структуры меняла смысл
  уже собранных ответов задним числом.
- **`hash = md5(ID элемента + '_' + ID сделки)`.** Ключ публичной ссылки предсказуем: зная пару
  идентификаторов, чужую анкету можно открыть перебором. В новом — криптостойкий случайный токен,
  в БД только его хеш.
- **Публичная страница без ограничений.** Нет TTL, нет одноразовости, нет rate-limit, а в шапке
  шаблона стоит `<meta name="robots" content="all">` — анкеты индексируемы. Всё три пункта
  закрываем на уровне роута `/s/[token]`.
- **Статусы, которые ничего не защищают.** Статусная машина в карточке есть (`STATUS`:
  `NEW`/`WORK`/`FILL`/`CLOSE`), но публичный компонент её не проверяет: `sendQuestionareForm`
  находит анкету по хешу и сразу пишет ответы, независимо от статуса. Повторный сабмит перезаписывал
  ту же строку и заново запускал бизнес-процесс (`finish()` → шаблон БП 273). В новом статус должен
  быть не пометкой для менеджера, а условием приёма ответа.
- **Vue 2 через `BX.Vue`, вёрстка на `landing24`, зависимость от `shef.b24base`.** Уходим на Nuxt 4
  и `b24ui`.

## 19. Запросы, чтобы снять фактуру со старого портала

Миграция данных не делается — выборки нужны только как фактура для проектирования: структура анкет,
как реально пользовались шкалой и что писали в текстовых полях.

Каждая пачка — один запрос, который возвращает одну таблицу: вставил, выполнил, снял результат.
Пачку 2 нужно прислать текстом, а не скриншотом — там длинный JSON в одной ячейке.

### Пачка 1. Что вообще есть: инфоблок, HL-таблицы, ключи настроек

```sql
SELECT 'iblock' AS src, CAST(ID AS CHAR) AS a, CODE AS b, NAME AS c, CAST(VERSION AS CHAR) AS d
FROM b_iblock WHERE ID = 67
UNION ALL
SELECT 'hlblock', CAST(ID AS CHAR), TABLE_NAME, NAME, ''
FROM b_hlblock_entity WHERE TABLE_NAME LIKE 'sh\_qest\_h\_%'
UNION ALL
SELECT 'option', '', NAME, LEFT(VALUE, 120), CAST(CHAR_LENGTH(VALUE) AS CHAR)
FROM b_option WHERE MODULE_ID = 'shef.questionary';
```

Колонка `d` у строки `iblock` — это `VERSION`. От неё зависит пачка 5.

### Пачка 2. Структура анкет и реестр типов — текстом, не скрином

```sql
SELECT NAME, VALUE FROM b_option WHERE MODULE_ID = 'shef.questionary' ORDER BY NAME;
```

Самая ценная выборка из всех: `questionary_list` — реестр типов, `questionary_group_<тип>` — секции,
поля, веса `SIZE` и диапазоны `TERMS`. Это прямой донор для сидов шаблонов опросов.

### Пачка 3. Свойства карточки анкеты и значения списка TYPE

```sql
SELECT 'prop' AS kind, p.ID AS id, p.CODE AS code, p.NAME AS name,
       p.PROPERTY_TYPE AS ptype, p.MULTIPLE AS multi, p.SORT AS srt, '' AS xml_id
FROM b_iblock_property p WHERE p.IBLOCK_ID = 67
UNION ALL
SELECT 'enum', e.ID, p.CODE, e.VALUE, 'L', '', e.SORT, e.XML_ID
FROM b_iblock_property_enum e
JOIN b_iblock_property p ON p.ID = e.PROPERTY_ID
WHERE p.IBLOCK_ID = 67
ORDER BY kind, srt;
```

### Пачка 4. Все вопросы всех анкет как поля HL-блоков

```sql
SELECT h.TABLE_NAME AS tbl, f.FIELD_NAME AS fld, f.USER_TYPE_ID AS utype,
       f.MANDATORY AS req, f.MULTIPLE AS multi, f.SORT AS srt, l.EDIT_FORM_LABEL AS title
FROM b_user_field f
JOIN b_hlblock_entity h ON f.ENTITY_ID = CONCAT('HLBLOCK_', h.ID)
LEFT JOIN b_user_field_lang l ON l.USER_FIELD_ID = f.ID AND l.LANGUAGE_ID = 'ru'
WHERE h.TABLE_NAME LIKE 'sh\_qest\_h\_%'
ORDER BY h.TABLE_NAME, f.SORT;
```

Сопоставив это с пачкой 2, получаем полную картину: какой вопрос в какой секции и с каким весом.

### Пачка 5. Объём, статусы и средние баллы (под `VERSION = 2`)

Собрано под реальные идентификаторы свойств из пачки 3.

```sql
SELECT YEAR(el.DATE_CREATE)                AS y,
       COALESCE(tp.XML_ID, '(нет)')        AS type_code,
       COALESCE(st.XML_ID, '(нет)')        AS status,
       COUNT(*)                            AS cnt,
       SUM(CASE WHEN ps.PROPERTY_372 IS NOT NULL AND ps.PROPERTY_372 <> '' THEN 1 ELSE 0 END) AS answered,
       ROUND(AVG(CAST(NULLIF(ps.PROPERTY_365, '') AS DECIMAL(10,2))), 2) AS avg_product,
       ROUND(AVG(CAST(NULLIF(ps.PROPERTY_366, '') AS DECIMAL(10,2))), 2) AS avg_process,
       ROUND(AVG(CAST(NULLIF(ps.PROPERTY_367, '') AS DECIMAL(10,2))), 2) AS avg_personal
FROM b_iblock_element el
JOIN b_iblock_element_prop_s67 ps ON ps.IBLOCK_ELEMENT_ID = el.ID
LEFT JOIN b_iblock_property_enum tp ON tp.ID = ps.PROPERTY_364
LEFT JOIN b_iblock_property_enum st ON st.ID = ps.PROPERTY_362
WHERE el.IBLOCK_ID = 67
GROUP BY y, type_code, status
ORDER BY y, type_code, status;
```

Средние по секциям здесь особенно полезны: они уже посчитаны системой и сразу показывают, работает
шкала 0–10 или всё жмётся к верхней границе.

### Пачка 6. Генератор: распределение оценок по каждому балльному вопросу

Имена HL-таблиц заранее неизвестны, поэтому запрос не считает, а **пишет SQL**. Выполняешь его,
получаешь столбец готовых строк, склеиваешь их в один запрос (у последней строки убрать хвостовой
`UNION ALL`) и выполняешь второй раз.

```sql
SELECT CONCAT(
  'SELECT ''', h.TABLE_NAME, ''' AS t, ''', f.FIELD_NAME, ''' AS f, ',
  f.FIELD_NAME, ' AS v, COUNT(*) AS c FROM ', h.TABLE_NAME,
  ' WHERE ', f.FIELD_NAME, ' IS NOT NULL GROUP BY v UNION ALL'
) AS sql_text
FROM b_user_field f
JOIN b_hlblock_entity h ON f.ENTITY_ID = CONCAT('HLBLOCK_', h.ID)
WHERE h.TABLE_NAME LIKE 'sh\_qest\_h\_%' AND f.USER_TYPE_ID = 'double'
ORDER BY h.TABLE_NAME, f.SORT;
```

Здесь и виден ответ на главный вопрос по шкале: если по всем вопросам масса значений сидит на 9–10,
шкала 0–10 не различает клиентов и в новом решении её надо менять.

### Пачка 7. Генератор: тексты и заполняемость

Тот же приём для текстовых полей — примеры ответов и доля пустых.

```sql
SELECT CONCAT(
  'SELECT ''', h.TABLE_NAME, ''' AS t, ''', f.FIELD_NAME, ''' AS f, COUNT(*) AS total, ',
  'SUM(CASE WHEN ', f.FIELD_NAME, ' IS NULL OR ', f.FIELD_NAME, ' = '''' THEN 0 ELSE 1 END) AS filled, ',
  'MAX(CHAR_LENGTH(', f.FIELD_NAME, ')) AS max_len FROM ', h.TABLE_NAME, ' UNION ALL'
) AS sql_text
FROM b_user_field f
JOIN b_hlblock_entity h ON f.ENTITY_ID = CONCAT('HLBLOCK_', h.ID)
WHERE h.TABLE_NAME LIKE 'sh\_qest\_h\_%' AND f.USER_TYPE_ID = 'string'
ORDER BY h.TABLE_NAME, f.SORT;
```

Плюс десяток живых ответов глазами — по одной таблице из пачки 1:

```sql
SELECT * FROM sh_qest_h_<код> ORDER BY ID DESC LIMIT 20;
```
