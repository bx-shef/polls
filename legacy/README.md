# Материалы по старому решению заказчика

Всё в этой папке — про источник миграции, а не про новое приложение. Нужно, когда дойдёт до
адаптера импорта.

| Файл | Что это |
|---|---|
| `LEGACY-ANALYSIS.md` | разбор: где что лежало, как считались баллы, что показали накопленные данные |
| `questionary-structure.txt` | структуры анкет из `b_option` — прямой донор для сидов шаблонов |
| `audit-queries.sql` | запросы, которыми снималась фактура, собранные под реальные таблицы |

## Оговорки к `questionary-structure.txt`

Файл — **реконструкция**, а не машинная выгрузка: кириллица раскодирована из `\uXXXX` для
читаемости, и в нём одиннадцать анкет из двенадцати — конфигурация `digital` не попала, её надо
снять с портала заново. Для адаптера миграции берите свежую выгрузку запросом, а этот файл
используйте как справку о форме данных.

Что в этих структурах важно знать заранее:

- веса внутри секции везде дают ровно 100, шкала у всех вопросов `0…10`;
- вес `0` используется как способ выключить вопрос из оценки — в новой модели это отдельный флаг;
- в анкете `game` вопрос `UF_HQ_PROC_REG` стоит в двух секциях сразу с разными весами: при импорте
  расщепляется на два ключа, обоим при пересчёте отдаётся одно значение;
- диапазоны интерпретации (`TERMS`) заполнены только у `digital`, и нижняя граница начинается с 4 —
  клиент с оценкой ниже не видел никакого текста;
- тексты интерпретации хранятся готовым HTML с классами `landing24`, при импорте вычищаются
  до текста.

## Ловушка с датами

`SEND_DATE` в карточке — это дата **заполнения**: она ставилась в момент сохранения ответа.
Настоящая дата отправки клиенту лежит в `DATE_C_SEND`. Перепутать — значит сдвинуть всю хронологию
отчётов.
