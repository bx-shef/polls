# Развёртывание

Здесь описано, что делает человек руками. Автоматизации подключения доменов нет и не
планируется: домен — предмет договорённости, а не функция приложения
(`docs/PROCESS.md`, раздел 8).

## Что из чего состоит

| Файл | Что делает |
|---|---|
| `Dockerfile` | три стадии: зависимости → сборка → runtime; наружу отдаёт `.output` Nitro, миграции и их запускалку |
| `compose.yaml` | прод-стек: приложение, Postgres, Redis, nginx, Watchtower |
| `nginx.conf` | TLS, зоны ограничения частоты, анонимизация адресов в логах, CSP |
| `proxy-headers.conf` | заголовки к апстриму, общие для всех location |

Сети две. `internal` помечена `internal: true` — база и Redis не имеют выхода в интернет
и портов на хост. Наружу смотрит только nginx.

## Первое развёртывание

Команды ниже прогнаны целиком в контейнерах — с самоподписанным сертификатом вместо
Let's Encrypt, потому что выпустить настоящий можно только на живом домене.

1. **DNS.** `A`-запись `polls.bx-shef.by` на адрес хоста. Убедиться, что резолвится,
   **до** выпуска сертификата: Let's Encrypt проверяет владение доменом по HTTP,
   и на неготовом DNS выпуск сгорит вместе с лимитом попыток.

2. **Репозиторий на хост.** Достаточно каталога `deploy/`, `Makefile` и файла
   `deploy/.env`:

   ```
   POSTGRES_PASSWORD=…            # обязательно, стек без него не поднимется
   PUBLIC_BASE_URL=https://polls.bx-shef.by
   APP_IMAGE=ghcr.io/bx-shef/polls:latest
   LOG_LEVEL=info
   ```

   Проверить, что compose видит переменные: `docker compose -f deploy/compose.yaml config`.

3. **Сертификат.**

   ```bash
   make cert DOMAIN=polls.bx-shef.by EMAIL=…
   ```

   Команда сама поднимает временный nginx с `nginx-bootstrap.conf` на 80 порту,
   отдаёт каталог проверки и гасит его после выпуска. Отдельный конфиг здесь нужен
   не для красоты: боевой `nginx.conf` ссылается на файлы сертификата и без них
   не стартует вообще, а сертификата на чистом хосте ещё нет.

   Продление — `make cert-renew` задачей cron раз в сутки; на работающем стеке оно
   само перечитывает конфигурацию nginx.

4. **Запуск.**

   ```bash
   make prod-pull
   make prod-up
   make prod-migrate       # схема накатывается одноразовым запуском того же образа
   ```

5. **Проверка.**

   ```bash
   curl -s https://polls.bx-shef.by/api/health
   ```

   Ожидается `"status":"ok"` и `db`/`redis` в состоянии `ok`.

   | Что видно | Что это значит |
   |---|---|
   | `db: down` | не накатились миграции или пароль разошёлся с `deploy/.env` |
   | `redis: down` | контейнер Redis не поднялся, смотреть `docker compose -f deploy/compose.yaml logs redis` |
   | соединение не устанавливается | nginx не стартовал — почти всегда нет файлов сертификата, шаг 3 |
   | 502 от nginx | приложение ещё поднимается либо упало, смотреть `make prod-logs` |

## Обновление

Watchtower проверяет реестр раз в пять минут и подменяет только контейнеры с меткой
`com.centurylinklabs.watchtower.enable=true` — то есть само приложение. База, Redis и
nginx не трогаются никогда: подменить базу под нагрузкой из-за нового тега — не та цена,
которую стоит платить за удобство.

Миграции Watchtower не накатывает. Если релиз меняет схему — `make prod-migrate` руками,
до выкатки образа. Это единственное место, где автообновление опасно: оно подменит
контейнер по расписанию, не спросив, готова ли под него база. Пока релизов со сменой
схемы мало, дешевле помнить об этом, чем строить оркестрацию.

Версия API Docker у Watchtower задана явно (`DOCKER_API_VERSION`): его собственная
слишком стара для Docker 25 и новее, и без этой переменной сервис молча уходит в цикл
перезапусков — обновления при этом просто не происходят.

## Домен клиента

Второй `server`-блок в `nginx.conf` со своим `server_name` и своим сертификатом, плюс
`portals.public_host` у нужного портала. Ссылки на анкету генерируются от этого поля,
поэтому уже выданные ссылки на старом домене продолжают работать, пока живёт его
сертификат.
